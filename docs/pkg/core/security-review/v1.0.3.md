## サマリー

致命的な脆弱性は **検出されず** (信頼度 0.7 以上の所見ゼロ)。本バージョンの差分は ID3v2.2 `PIC` フレームの読み取り修正のみで、ランタイム依存・ファイル I/O・公開 API に変更なし。

差分の中身:

- `convertPicBodyToApicBody` (新規): v2.2 `PIC` ボディ (`<encoding:1><format:3><kind:1><desc><data>`) を v2.3 `APIC` レイアウト (NUL 終端 MIME) に書き換え。既知 3 文字フォーマット (PNG/JPG/GIF/BMP/TIF) を MIME にマップ、リンク画像の `-->` は維持、未知値は `image/<小文字化した値>` に変換
- `parseV22Frame`: `PIC` → `APIC` 昇格時に上記変換を適用 (従来はボディ未変換のままで、MIME 不正値化と画像データ先頭の欠損を招いていた)
- `apicToPicture`: MIME を `detectMime(data) ?? 宣言 MIME ?? "image/jpeg"` に変更 (iTunes の「PNG 宣言 + JPEG 実データ」不一致対策)

境界チェックの検証: `convertPicBodyToApicBody` の全スライスは `body.length < 5` の早期 return でガードされ、`subarray` は JS 仕様上クランプされるため範囲外読み取りは構造的に発生しない。`MIME_BY_FORMAT` はプロトタイプ汚染経路なし (3 文字固定入力のためキー `__proto__` 等は到達不能、値参照は `??` フォールバックで undefined 安全)。書き込み経路は `buildFrame` がフレーム サイズを `data.length` から再計算するため、変換で長くなったボディが preserved frames 経由で `writeMp3` / `writeWav` / `writeAiff` に流れてもサイズ不整合 (frame smuggling) は生じない。

## 良い点 (Strengths)

- **スニッフィング優先は攻撃者の制御を狭める方向** — `detectMime` が返すのは受動的なラスタ画像 6 種 (JPEG/PNG/GIF/BMP/TIFF/WebP) のみで、実データのマジックバイトが宣言 MIME を上書きする。攻撃者が MIME 文字列を自由文字列として下流 (GUI の Blob type / 展開時拡張子) へ届ける余地はむしろ減少した。
- **合成 MIME の形が有界** — 未知フォーマットから合成される MIME は `image/` + 最大 3 文字 (小文字化済み) に収まり、`text/html` や `application/*` などアクティブ コンテンツ型を偽装できない。
- **GUI 側のシンクも安全を確認** — 展開時の拡張子は `extensionForMime` の許可リスト (未知は `"bin"`) で決まり、プレビューは `<img>` への Blob URL のみ。`-->` (リンク画像) の URL を参照・フェッチするコードは存在しない。

## 所見 (Findings)

### INFO-1 — フォーマット 3 バイト内の NUL によるフィールド境界ズレ

- **内容**: `PIC` のフォーマット 3 バイト内に NUL を含む細工 (例: `P\0G`) をすると、変換後の APIC ボディの再パースでフィールド境界が本来と異なる位置になり得る。
- **評価**: 到達し得るフィールド値はすべて、攻撃者が v2.3 APIC フレームを直接細工すれば最初から自由に設定できる範囲に収まる。信頼境界を越える新しいデータフローはなく、悪用経路なし。confidence 0.2 で報告閾値未満。
- **対応**: 現状維持。末尾の NUL / 空白は変換時に除去済み。

### INFO-2 — MIME スニッフィング優先による宣言値との乖離 (parser differential)

- **内容**: 宣言 MIME と実データが食い違うファイルで、本ライブラリは実データ側 (`detectMime`) を採用するため、宣言値をそのまま信じる他実装とはメタデータの報告値が異なり得る。
- **評価**: macOS Music / Finder・ATL.NET と同じ「実データ優先」の挙動であり、宣言値を無検証で下流に渡すよりも安全側。スニッフィング不能な場合のフォールバック順 (宣言値 → `image/jpeg`) は従来挙動と同一。悪用シナリオなし。
- **対応**: 現状維持。MIME を厳密に検証する用途では `PictureInfo.data` の再検査を推奨。

v1.0.0 の LOW-1〜LOW-6 について、本差分での悪化はなし (ファイル I/O・公開 API・タグ検証経路に変更なし)。v1.0.2 の INFO-1 / INFO-2 (MP4 末尾ゴミ) にも影響なし。

## 次回更新時のチェックリスト

core のバージョンを上げる PR では新しい `v1.x.y.md` を作成し、以下を再評価:

- [ ] v1.0.0 の LOW-1〜LOW-6 (シンボリック リンク follow ほか) が当該 PR で悪化していないか
- [ ] `detectMime` に新しいシグネチャ (特に SVG などアクティブ コンテンツになり得る形式) を追加する場合は、GUI のプレビュー / 展開シンクでの扱いを再評価
- [ ] v2.2 由来フレームの変換対象を `PIC` 以外 (RVA / EQU など v2.3 とレイアウトが異なるフレーム) に広げる場合は、変換後ボディの再パース境界を再検証
- [ ] `dependencies` にランタイム依存を追加した場合は、当該パッケージの既知 CVE を `npm audit` / GitHub Advisory で確認
