## サマリー

致命的な脆弱性は **検出されず** (Critical / High / Medium 0 件)。本差分は呼び出し側が渡すタグ値の「状態」を `undefined` (保持) / `null` (削除) / `""` (削除) の 3 値に拡張し、各 writer の分岐をそれに合わせて統一するもの。バイナリ パーサー、ファイル I/O、依存関係には変更がなく、ランタイム `dependencies` は引き続き存在しない。

|  | 件数 (差分起因) | 件数 (継続) |
| --- | --- | --- |
| Critical | 0 | 0 |
| High | 0 | 0 |
| Medium | 0 | 0 |
| Low / Informational | 0 | v1.0.0 の LOW-1〜LOW-6 / v1.0.2〜v1.0.4 の INFO / INFO-1 (`ID3V1_GENRES` freeze 未実施) (据え置き) |

検証した攻撃経路と結論:

1. **`applyTagPatch` / `fillNumberPairs` の動的キー経由 prototype pollution** — `applyTagPatch` は `Object.entries(patch)` でキーを列挙し、`{ ...existing }` で生成したローカル オブジェクトへ `out[field] = value` / `delete out[field]` する。`patch` に `__proto__` キーを含めた検証では、文字列値 (型が許す唯一の形) は setter に無視され、オブジェクト値 (JSON などで型を迂回した場合) もローカル `out` の prototype を差し替えるだけで **グローバルな `Object.prototype` は汚染されない**。後続の `tagDataToExtendedDescriptors` は固定の名前付きフィールドだけを読み、動的キーをバイナリ出力へ流さないため、同じ呼び出し側が `album: "..."` を直接渡す以上の効果は得られない。`fillNumberPairs` は書き込み先キーを固定表 `PAIRS` に限定し、`existing` の値はファイル reader 由来の数値のみ。`WriteOptions.tag` は同一プロセス・同一権限の呼び出し側が供給する値であり、信頼境界を越える入力ではない (従来レビューと同じ脅威モデル)。
2. **`mergeProducerFrame` の NUL 除去** — `producer === undefined` の早期 return の後で `(producer ?? "").replaceAll("\u0000", "")` を適用しており、`null` は `""` (role 削除) として既存経路に合流する。TIPL / IPLS の NUL 区切りリストへの injection 経路は増えていない。
3. **MP4 tombstone と細工されたソース ファイル** — tombstone (`values: []`) は `tagToItunesAtoms` が呼び出し側の patch から生成する `incoming` 側でのみ判定し、`existing` 側 atom は name / freeform key の一致だけで扱う。`data` 子 atom を持たない ilst atom がソースに含まれる場合 (`readIlstEntry` が `values: []` を返す) も従来どおり verbatim で引き継がれ、削除マーカーと誤認されることはない。
4. **`null` がエンコーダーへ到達する経路** — `utf8Value` / `beSignedIntValue` / `encodeText` / `String()` / `stringifyValue` の各呼び出しは `hasTagValue` (型ガード) または `?? ""` で保護され、`tsc --noEmit` も通過。writer 側に `Partial<TagData>` を受ける古いシグネチャは残っていない。Vorbis Comment / APE のキー検証 (`=` / NUL / 非印字文字 / 長さ) は新コードの下流で変更なく機能し、キーは引き続き `FIELD_KEYS` の固定定数のみ。
5. **`numberPairAtom` / `numberAndTotalValue` の範囲処理** — 削除・未指定側を `0` に置換する挙動は従来の `?? 0` と同一で、`writeUInt16BE` の範囲外 `RangeError` も不変。`fillNumberPairs` が補完に使う MP4 の既存値は `readUInt16BE` 由来 (0..65535) で範囲外にならない。
6. **その他** — ファイル パス処理、認証、暗号、デシリアライズ、`eval` の追加・変更なし (`saveTrack.ts` は型のみ、`mme.ts` はエクスポート追加のみ)。`fillNumberPairs` が既存タグから複製するのは同一ファイル内の `trackNumber` / `trackTotal` / `discNumber` / `discTotal` に限られ、データ露出経路もない。

## 良い点 (Strengths)

- **判定の一元化** — 「値あり / 削除 / 保持」の判定を `utils/tagPatch/hasTagValue` / `isClearedValue` の型ガードに集約し、各 writer が `null` を個別に扱う必要をなくしている。エンコーダー呼び出しの直前で型が `string` / `number` に narrowing されるため、`null` の取りこぼしがコンパイル時に検出される。
- **既存のサニタイズ経路を維持** — `mergeProducerFrame` の NUL 除去、Vorbis Comment / APE のキー検証など、従来レビューで確認済みの防御を迂回する新経路を作っていない。
- **ファイル由来データと patch の分離** — MP4 tombstone は呼び出し側 patch から生成した atom にのみ適用し、パース済み atom の内容 (`values` の有無) を制御信号として解釈しない。
- **固定キー表による書き込み** — `fillNumberPairs` / `tagDataToExtendedDescriptors` / `tagToItunesAtoms` はいずれも書き込み先キーを定数表に限定しており、呼び出し側の任意キーがタグのキー名として出力されることはない。
- **検証済** — `pnpm typecheck` / `pnpm check` / `pnpm build` / `pnpm test` (core 549 件、cli 248 件、gui 289 件) が全通過。

## 所見 (Findings)

**該当なし**。継続項目 (v1.0.0 の LOW-1〜LOW-6、v1.0.2〜v1.0.4 の INFO、INFO-1) は本差分で変更されたコードに該当せず据え置き (悪化なし)。
