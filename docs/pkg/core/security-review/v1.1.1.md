## サマリー

致命的な脆弱性は **検出されず** (Critical / High / Medium 0 件)。本差分は `TagData.rating` (正規化値 `[0, 1]`) を ID3v2 / Vorbis Comment / APE で読み書きするもので、呼び出し側の `rating` は number をクランプ・半星へ丸めてからバイト列に落とし、ファイル由来で出力へ戻るバイト列 (POPM の e-mail と再生カウンター) は同一ファイル内で正しいサイズのフレームに再格納される。タグのキーは定数のみで、ファイル I/O・デシリアライズ・動的キー・依存関係の変更はない。

|  | 件数 (差分起因) | 件数 (継続) |
| --- | --- | --- |
| Critical | 0 | 0 |
| High | 0 | 0 |
| Medium | 0 | 0 |
| Low / Informational | 1 (INFO-2、本 PR 内で対処済) | v1.0.0 の LOW-1〜LOW-6 / v1.0.2〜v1.0.4 の INFO / INFO-1 (`ID3V1_GENRES` freeze 未実施) (据え置き) |

検証した攻撃経路と結論:

1. **細工・切り詰められた `POPM` 本体の解析** (`parsePopularimeterFrame`) — 空本体 / NUL なし / 末尾 NUL は `terminator === -1 || terminator + 1 >= body.length` で拒否。受理時は rating byte の添字が範囲内であることが保証され、カウンターの `subarray` は空にクランプされる。`undefined` が writer に到達する経路はない。
2. **ファイル由来カウンター バイト列の再出力** (`buildPopularimeterFrameBody` / `mergeRatingFrame`) — フレーム サイズは既存の `buildFrame` が本体長から算出 (v2.3 は UInt32BE、v2.4 は syncsafe + `RangeError` ガード) し、タグ ヘッダーのサイズも構築済みフレームの合計から求めるため、任意長・任意内容のカウンターで他フレームやタグ サイズを狂わせることはできない。カウンター長は元タグ本体 (パーサーが `dataStart + size > body.length` を拒否) に上限づけられる。70,000 バイトの `0xFF 0x00` / `0xFF 0xE0` 列を含むカウンターが v2.3 / v2.4 でバイト単位で往復し、隣接する `TIT2` / `TXXX` が保たれることを検証。
3. **POPM e-mail への NUL 注入** — 文字列段階の `replaceAll("\u0000", "")` は `Buffer.from(s, "latin1")` が 0xFF 超のコード ポイントを下位バイトに切り詰める (`"Ā"` → `0x00`) ため迂回されうる (INFO-2)。e-mail は呼び出し側から指定できず、供給元はファイル バイト列の `decodeText(..., "latin1")` (≤ 0xFF のみ) と定数 `POPM_DEFAULT_EMAIL` に限られるため **悪用不可** だが、防御的に Latin-1 エンコード後のバイト列から `0x00` を除去する実装へ変更し、テストを追加した。
4. **`mergeRatingFrame` の信頼境界** — 最初の `POPM` だけが e-mail / カウンターを提供し、残りは破棄。データは同一ファイル内で完結し、他ファイル・他ユーザーへの露出はない。`null` は全 `POPM` を削除、`undefined` は verbatim 保持。`hasTagValue` により `null` は `encodePopmRating` に到達しない。
5. **ファイル由来テキストの `decodePercentRating`** — `"Infinity"` / `"-Infinity"` / `"1e400"` / `"NaN"` / `""` / `"-1"` / 全角・アラビア数字は `undefined`、`"-0"` は `-0` (無害)、`"0x10"` は `0`、`"5abc"` は `1`。戻り値は常に `[0, 1]` の有限値または `undefined` で、`TagData.rating` への代入にのみ使われ、バイト writer に直接渡らない。
6. **`decodePopmRating` / `encodePopmRating` の範囲外・NaN 入力** — `encodePopmRating(NaN)` は添字 `NaN` → `?? 0` で `0`、`±Infinity` はクランプ。`decodePopmRating(NaN)` は `1` を返すが入力はパース済みバイト (0..255) のみで到達不能。`buildPopularimeterFrameBody` は rating byte を追加でクランプ・丸め、`NaN` は `Buffer` 代入で `0` になる。
7. **`stringifyValue(field, value)` と Vorbis / APE writer** — number の rating は `encodePercentRating` により ASCII 数字 (`"0"`..`"100"`) のみを出力。キーは `FIELD_KEYS` の定数 `RATING` / `Rating` / `Preference` で、既存の `writeVorbisComment` / `writeItem` の検証 (`=` / NUL / 非印字文字 / 長さ) を通過する。呼び出し側の `NaN` は値側の `"NaN"` テキストになる (読み戻しは `undefined`) だけで、新しい injection 面はない。
8. **reader のディスパッチ** — `apeTagToTagData` / `vorbisCommentToTagData` は固定表 `FIELD_MAP` の結果で分岐し、`id3v2TagToTagData` は `POPM_FRAME_ID` で判定して最初のフレームのみ採用。動的キーや prototype pollution の経路は追加していない。
9. **その他** — 認証 / 認可、暗号、シークレット、パス処理、デシリアライズ、`eval` 相当のコードには触れておらず、`dependencies` の変更もない。`POPM_DEFAULT_EMAIL` は広く知られた公開識別子文字列で個人情報ではない。

## 良い点 (Strengths)

- **既存パターンの踏襲** — `POPM` のマージは `mergeProducerFrame` (involved people) と同じ構造 (`undefined` 保持 / `null` 削除 / 既存フレームの付随データ保持) で実装され、NUL 除去などの防御も同等以上。
- **数値変換の閉域化** — `encodePopmRating` は固定表 (11 要素) への丸め済み添字アクセス、`encodePercentRating` は `Math.round(clamp * 100)` のみで、出力が有限の ASCII 数字に限定される。
- **フレーム サイズの一元計算** — 新しいフレーム本体も既存の `buildFrame` / `buildHeader` を経由するため、長さの不整合を作れない。
- **検証済** — `pnpm typecheck` / `pnpm check` / `pnpm build` / `pnpm test` (core 617 件、cli 248 件、gui 289 件) が全通過。

## 所見 (Findings)

### INFO-2: POPM e-mail の NUL 除去が Latin-1 の下位バイト切り詰めを考慮していなかった (対処済)

- **箇所**: `packages/core/src/tags/id3v2/popularimeter/buildPopularimeterFrameBody.ts`
- **内容**: 文字列段階で `\u0000` を除去した後に Latin-1 エンコードしていたため、`U+0100` のようなコード ポイントが `0x00` に変換され e-mail と rating byte の境界をずらせる可能性があった。e-mail の供給元がファイル由来 (Latin-1 デコード済) と定数のみのため悪用経路はない。
- **対処**: エンコード後のバイト列から `0x00` を除去する実装に変更し、`buildPopularimeterFrameBody.test.ts` に `U+0100` を含むケースを追加。

継続項目 (v1.0.0 の LOW-1〜LOW-6、v1.0.2〜v1.0.4 の INFO、INFO-1) は本差分で変更されたコードに該当せず据え置き (悪化なし)。
