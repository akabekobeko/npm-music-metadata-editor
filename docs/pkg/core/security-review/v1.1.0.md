## サマリー

致命的な脆弱性は **検出されず** (Critical / High / Medium 0 件)。本差分は `detectMp3Signature` の MPEG sync 検出を「先頭 64 バイト窓のスキャン」から「offset 0 のみ」へ狭め、あわせて `mme.ts` の登録順を強いマジックを持つフォーマット優先 (MP3 を最後) に変更するもの。検出条件の縮小と優先順位変更が新たな攻撃経路を開かないかを重点的に検証した。

|  | 件数 (差分起因) | 件数 (継続) |
| --- | --- | --- |
| Critical | 0 | 0 |
| High | 0 | 0 |
| Medium | 0 | 0 |
| Low / Informational | 0 | v1.0.0 の LOW-1〜LOW-6 / v1.0.2〜v1.0.4 の INFO (据え置き) |

検証した攻撃経路と結論:

1. **受理集合の変化** — 新しい `detectMp3Signature` の受理集合は旧実装の**厳密な部分集合** (旧実装で拒否され新実装で受理される入力は存在しない)。判定に使う `parseMp3AudioHeader` は既存・無変更で、`offset + 4 > bytes.length` の境界ガードとテーブル参照のフォールバック (`?.` / `?? 0`) を備える。
2. **フォーマット混同 (format confusion)** — 従来は先頭 64 バイト内に `0xFF Ex/Fx` を含むだけで MP4 / FLAC 等が MP3 リーダー/ライターへ誤ルーティングされ得た (書き込み経路では誤った形式でのファイル再構築につながる)。本差分はこの混同クラスを**縮小**する。逆方向 (真の MP3 が他形式へ誤検出される経路) は、ファイルが offset 0 に他形式の強いマジックを持つ場合に限られ、その場合は構造上その形式そのものであるため新たな混同は生じない。
3. **可用性への影響** — 先頭にゴミがあり拡張子も `.mp3` でないファイルは検出失敗 (`unsupported-format` エラー) となるが、これは機能面の挙動変更であり脆弱性ではない。`.mp3` 拡張子のファイルは `detectFormat` の拡張子フォールバックで従来どおり解決される (拡張子は signature が全滅した場合のみ信頼されるため、強いマジックを上書きすることはない)。
4. **新規攻撃面の不在** — 新しいパース経路・ファイル I/O・パス操作・動的評価・データ露出はいずれも追加されていない。テスト追加分は合成バイト列のみで出荷コードに影響しない。

## 良い点 (Strengths)

- **ヒューリスティックの最小化** — 実効マジックが約 2 バイトしかない MPEG sync 判定を offset 0 に限定し、任意バイナリ (MP4 `mvhd` タイムスタンプ等) との偶然一致による誤検出クラスを構造的に排除している。
- **優先順位の明示** — 登録順を「強いマジック先行・ヒューリスティック最後」とし、その根拠を `mme.ts` のコメントに明文化。将来フォーマットを追加する際の指針になる。
- **実データ由来の回帰テスト** — 実ファイルで観測された `mvhd` タイムスタンプ バイト列 (`FF FC 64 D1`) をフィクスチャ化し、単体 (`detectMp3.test.ts`) と実登録での統合 (`mme.test.ts`) の両方で回帰を固定している。

## 所見 (Findings)

**該当なし**。継続項目 (v1.0.0 の LOW-1〜LOW-6、v1.0.2〜v1.0.4 の INFO) は本差分で変更されたコードに該当せず据え置き (悪化なし)。
