## サマリー

致命的な脆弱性は **検出されず** (Critical / High / Medium 0 件)。本差分は `parseAtomTree` の末尾ゴミ許容条件を「type バイトが印字可能 ASCII でない場合」から「type が既知トップレベル atom type (17 種) でない場合」へ広げるもので、拒否ルールの緩和が新たな攻撃経路を開かないかを重点的に検証した。

|  | 件数 (差分起因) | 件数 (継続) |
| --- | --- | --- |
| Critical | 0 | 0 |
| High | 0 | 0 |
| Medium | 0 | 0 |
| Low / Informational | 0 | v1.0.0 の LOW-1〜LOW-6 / v1.0.2〜v1.0.4 の INFO (据え置き) |

検証した攻撃経路と結論:

1. **末尾に `mdat` を置いた細工ファイルによる書き込み破壊** — `ftyp | moov | 不正ヘッダー (印字可能な未知 type) | mdat` という構成は本差分で解析可能になるが、`reassembleFile` は最終 atom 以降のバイトを verbatim 維持し、`buildOffsetRemap` は旧 moov 末尾以降の `stco`/`co64` オフセットを moov サイズ差分でシフトする。末尾領域の物理移動量とオフセット シフト量が一致するため、書き換え後もデータ参照は整合し破壊は起きない。
2. **許容された末尾領域へのデータ潜伏 (smuggling)** — 末尾バイトは書き換えを通じて維持されるが、これは差分前も非印字 type のゴミや well-formed な未知 type のトップレベル box で同様に可能であり、新規の攻撃面ではない。
3. **パーサー差分 (parser differential)** — 許容された末尾に別の `moov` を仕込み、スキャン方式の他実装と解釈を分岐させる細工は理論上可能だが、差分前から非印字 type で成立し、本ライブラリは読み書きとも一貫してゴミ以前のツリーを使用するため、具体的な信頼境界の侵害には至らない。
4. **書き込み時の再パース安定性** — `applyChunkOffsetUpdates` が再構築後のバッファを再パースする際も、末尾バイトは不変のまま同一の許容判定が決定的に再適用され、ライブラリ内で読み書きの解釈が分岐しない。
5. **injection / eval / パス操作** — デコードした type 文字列の用途は `Set.has` 参照とエラー メッセージへの補間のみで、動的評価・ファイル パス・シリアライズには到達しない。

## 良い点 (Strengths)

- **ガードレールの維持** — 入れ子コンテナーは従来どおり strict、`moov` 解析前のトップレベル ゴミは拒否、既知 type (`mdat` / `uuid` 等) の truncation は引き続きエラーと、許容の三条件が明確に保たれている。
- **拒否ルールの根拠強化** — 「偶然 4 バイトが印字可能になる確率 ≈ 2%」という旧判定の弱点を、既知 type の allowlist 照合 (偶然一致が事実上不可能) に置き換えており、判定の意味論が明確。
- **書き込み経路との整合** — 末尾ゴミの verbatim 維持 (`reassembleFile`) とオフセット リマップ (`buildOffsetRemap`) が差分と独立に整合しており、許容範囲の拡大が書き込み破壊を誘発しない設計になっている。
- **実データ由来のテスト** — 実ファイルで観測されたバイト列 (`"ReX`) をフィクスチャ化し、回帰を固定している。

## 所見 (Findings)

**該当なし**。継続項目 (v1.0.0 の LOW-1〜LOW-6、v1.0.2〜v1.0.4 の INFO) は本差分で変更されたコードに該当せず据え置き (悪化なし)。
