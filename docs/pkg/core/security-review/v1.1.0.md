## サマリー

致命的な脆弱性は **検出されず** (Critical / High / Medium 0 件)。本差分は、ファイル中に物理的に存在するタグ形式 (`"id3v2"` / `"ape"` / `"id3v1"`) を presence フラグの配列として読み取り結果へ載せる情報追加のみ。悪意あるオーディオ ファイルを起点とする攻撃経路を重点的に検証した。

|  | 件数 (差分起因) | 件数 (継続) |
| --- | --- | --- |
| Critical | 0 | 0 |
| High | 0 | 0 |
| Medium | 0 | 0 |
| Low / Informational | 0 | v1.0.0 の LOW-1〜LOW-6 / v1.0.2〜v1.0.4 の INFO / 前回の INFO-1 (`ID3V1_GENRES` freeze 未実施) (据え置き) |

検証した攻撃経路と結論:

1. **追加の `readId3v1` 呼び出し** — `readId3v1` は 128 バイト未満で `undefined` を返す事前ガードと固定オフセット読みのみで構成される既存・無変更の純関数。デフォルト `tagPriority` では従来から同一バイト列に対して実行されており、新たなパース経路は増えていない。`tagPriority` で `"id3v1"` を除外した場合にもパーサーが走るようになるが、安全性は同一。
2. **`tagSources` 経由のデータ露出** — 値は閉じたリテラル集合 (`"id3v2" | "ape" | "id3v1"`) で、攻撃者制御のバイト・長さ・文字列は一切流入しない。開示される情報 (どのタグ形式が存在するか) は呼び出し側が保持する入力から自明に導出可能で、信頼境界を越える開示はない。
3. **`loadTrack` のパススルー** — 固定キーのスプレッドのみで、prototype 汚染や injection の余地はない。
4. **`tagPriority` との意味的整合** — `tagSources` は priority フィルタと独立に「物理的な存在」を報告する仕様 (TSDoc に明記)。`tag` と `tagSources` の見かけ上の不一致は文書化された仕様であり、同一バイト列由来のため spoofing にはならない。

## 良い点 (Strengths)

- **閉じた語彙による報告** — 新フィールドの値域を既存の `TagSource` リテラル union に限定し、ファイル由来の任意文字列が公開 API 表面に漏れない設計。
- **presence 判定の再利用** — 既存パーサーの `undefined` 判定のみで構成し、新しいバイナリ解釈ロジックを追加していない。
- **仕様の明文化** — `tagPriority` フィルタとの独立性 (「存在」と「採用」の区別) を TSDoc とテストの両方で固定している。

## 所見 (Findings)

**差分起因の脆弱性は該当なし**。継続項目 (v1.0.0 の LOW-1〜LOW-6、v1.0.2〜v1.0.4 の INFO、前回の INFO-1) は本差分で変更されたコードに該当せず据え置き (悪化なし)。
